# ADR-004: Виділення release scanner у окремий мікросервіс

**Статус:** Прийнято

**Дата:** 2026-06-06

**Автор:** Maksym Paprotskyi

## Контекст

Спочатку застосунок працював як модульний моноліт: Fastify HTTP API для підписок та фоновий воркер в одному процесі, який періодично опитує GitHub на наявність нових релізів. Обидва bounded context-и спільно використовували один процес, один контейнер та одну базу даних PostgreSQL.

Сканування релізів має інший профіль виконання, ніж subscription API:

- періодичне опитування замість request/response трафіку
- окремі вимоги до масштабування та перезапуску (ліміти GitHub API, SMTP)
- вже ізольований за портовими інтерфейсами (`ScanTargetProvider`, `RepositoryStateUpdater`)

## Прийняте рішення

Виділити bounded context **release-scanner** в окремий worker-контейнер. Сервіс підписок залишається власником даних про підписки та надає невелике внутрішнє HTTP API для сканера.

### Межі сервісів

| Сервіс | Відповідальність | Доступ до даних |
|--------|------------------|-----------------|
| `app` (subscription API) | Публічне `/api/*`, внутрішнє `/internal/scanner/*`, PostgreSQL | Повний доступ до БД |
| `release-scanner` | Опитування GitHub, надсилання email про релізи | Без БД — лише HTTP |

### Контракт внутрішнього API

Усі маршрути мають префікс `/internal/scanner` та захищені `INTERNAL_API_KEY`.

| Метод | Шлях | Опис |
|-------|------|------|
| `GET` | `/scan-targets` | Повертає репозиторії з підтвердженими підписками та email підписників |
| `PATCH` | `/repositories/:id/last-seen-tag` | Оновлення `lastSeenTag` з optimistic locking |

У разі невдалого optimistic lock повертається `409 Conflict`.

### Комунікація

- Синхронний HTTP між сервісами (без message bus)
- Один кодовий репозиторій, два Docker-контейнери, різні `command`
- Контейнер сканера не має `DATABASE_URL`

### Конфігурація

- Обидва сервіси використовують спільний `INTERNAL_API_KEY`
- Сканер звертається до subscription API через `SUBSCRIPTION_API_URL`

## Наслідки

**Позитивні**

- Сканер можна перезапускати незалежно, не впливаючи на публічне API
- Чітке володіння даними підписок в одному сервісі
- Повторне використання наявної доменної логіки та портових абстракцій

**Негативні**

- Додатковий мережевий hop на кожному циклі сканування
- Вікно eventual consistency між сервісами (прийнятне для поточного масштабу)
- Операційна складність: два контейнери замість одного

## Розглянуті альтернативи

1. **Спільна база даних для сканера** — простіше підключення, але слабші межі сервісів і дублювання логіки доступу до даних
2. **Черга повідомлень** — краще розв'язування, зайве для ~10 користувачів та ~100 email/день
3. **Monorepo на npm workspaces** — сильніше розділення пакетів, надмірний рефакторинг для поточних потреб
